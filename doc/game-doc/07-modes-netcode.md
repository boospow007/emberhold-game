# 07 — PvP และ netcode แบบ server-authoritative (ร่าง v0.1)

- วันที่: 2026-09-08
- ที่มา: การตัดสินใจใน `01-direction.md` ข้อ 8.3 (PvP ทำทีหลัง, ไม่มี wave NPC, ทุกคนเท่าเทียม, รอครบแล้วค่อยเริ่ม, สไตล์ Yuri's Revenge) และข้อ 9 (netcode ปัจจุบันใช้กับ PvP ไม่ได้)
- สถานะ: ร่างแรกสำหรับวางแผนร่วมกัน ทุกข้อเป็น [เสนอ] ยกเว้นที่ระบุ [กำหนด]

## 1. สิ่งที่ตัดสินใจไปแล้ว

**[กำหนด]** (จาก 01-direction)
- PvP ทำหลัง Survival/Co-op เสร็จ (ตอนนี้เฟส 1–5 เสร็จแล้ว จึงเริ่มวางแผนได้)
- ต้องสร้างห้อง รอผู้เล่นครบและกดพร้อมทุกคนแล้วค่อยเริ่ม
- **ไม่มีศัตรู wave จาก NPC** ผู้เล่นสร้างฐานแล้วตีกันเองเท่านั้น
- **ทุกคนเท่าเทียม**: อัปเกรด Ember ไม่มีผล stack เท่ากัน เปิดทุกอย่างให้ครบ ยกเว้นของตกแต่ง
- ยังต้องตอบ: ใช้กฎทรัพยากร/สิ่งปลูกสร้างเต็มชุด หรือชุดย่อ

## 2. ทำไม netcode ปัจจุบันใช้กับ PvP ไม่ได้

ตอนนี้ **host เป็นคนจำลองเกม** แล้วอัปโหลด snapshot ผ่าน HTTP ทุก 180ms ส่วน guest ส่งแค่ input
- ใน co-op host โกงได้แต่ไม่มีเหตุจูงใจ ใน PvP host คือคู่แข่ง จึงแก้ตัวเลขได้ทุกอย่าง (เลือด ทรัพยากร ตำแหน่งศัตรู)
- HTTP polling หน่วง 200–400ms ต่อรอบ พอสำหรับ co-op แต่ PvP ที่ต้อง micro ทหารจะรู้สึกช้า
- ไม่มี fog of war ได้ เพราะทุก client เห็น World ทั้งก้อน

ดังนั้น PvP ต้องมี **ผู้จำลองที่เป็นกลาง** (server) หรือ **ทุกฝ่ายจำลองเหมือนกันแล้วตรวจสอบกัน** (lockstep)

## 3. ทางเลือกสถาปัตยกรรม

| | A. Server-authoritative (แนะนำ) | B. Deterministic lockstep | C. Host เดิม + ตรวจสอบย้อนหลัง |
|---|---|---|---|
| ใครจำลอง | server 1 ตัวต่อห้อง รัน `engine.step` ที่ 10 tick/วินาที | ทุก client จำลองเองจาก input ชุดเดียวกัน server เป็นแค่ตัวส่งต่อ input | host จำลอง server สุ่มตรวจ |
| กันโกง | ดีที่สุด client เห็นเฉพาะที่ server ส่ง ทำ fog of war ได้ | ดี (แก้ state ตัวเองไม่ได้เพราะอีกฝั่งจำลองเหมือนกัน) แต่ **maphack ได้** เพราะทุกคนมี World เต็ม | แย่ |
| ความหน่วง | input → server → ทุกคน ราว 60–150ms ต้องมี interpolation | ต้องรอ input ของทุกคนก่อนเดินเฟรม (input delay 100–200ms) คนหนึ่ง lag ทุกคนหยุด | เท่าปัจจุบัน |
| ต้นทุน server | CPU ตามจำนวนห้อง × tick (engine ตอนนี้ราว 1–3ms/tick) | ต่ำมาก | ต่ำ |
| late join / reconnect | ง่าย ส่ง snapshot จาก server | ยาก ต้อง replay input ทั้งหมดหรือส่ง state แล้ว hash ตรวจ | มีแล้ว |
| ความเสี่ยงทางเทคนิค | ต้องมีที่รัน loop ยาว (Durable Object หรือ server แยก) | engine ต้อง deterministic 100% ทุกเครื่อง (JS double เหมือนกัน แต่ต้องห้าม `Math.random`/เวลาจริงในทุกจุด) และ bug desync หายาก | ไม่แก้ปัญหา |
| ใช้ซ้ำกับ co-op | ได้ทันที แก้ปัญหา host หายและ host migration ไปในตัว | ได้ | — |

**[เสนอ] เลือก A** เพราะแก้ทั้งความยุติธรรม fog of war และปัญหา host หายของ co-op ในคราวเดียว ส่วน lockstep (ที่ Yuri's Revenge ใช้จริง) เหมาะกับเกมที่ต้นทุน server ต่ำเป็นเป้าหลัก แต่ maphack และ desync จะกินเวลาดีบั๊กมาก

**[คำถาม] ที่รัน server**
1. **Cloudflare Durable Object + WebSocket** ห้องละ 1 object รัน loop ด้วย `setInterval`/alarm ขณะมี WebSocket เชื่อมอยู่ อยู่ในระบบเดิม (D1, Worker) ไม่ต้องดูแล server แยก **ต้องยืนยันว่า OpenAI Sites hosting เปิด Durable Objects ให้ใช้** (`.openai/hosting.json` ตอนนี้มีแค่ d1/r2 และ `wrangler.json` ที่ build ออกมามี `durable_objects.bindings: []`)
2. **Server แยก** (Node บน Fly.io/Railway) รัน engine + WebSocket ยืดหยุ่นสุด แต่มีระบบต้องดูแลเพิ่ม และต้องแชร์ session cookie/ยืนยันตัวตนข้ามโดเมน
3. ถ้าทั้งสองไม่ได้: ใช้ lockstep (B) ผ่าน relay บน HTTP long-poll ซึ่งช้าและไม่แนะนำ

## 4. กติกา PvP

### 4.1 รูปแบบ
- **[เสนอ]** 1v1 ก่อน แล้ว 2v2 (ใช้ระบบทีมเดียวกัน) 4 คน free-for-all ไว้ทีหลัง
- แมตช์ยาวเป้าหมาย **15–25 นาที** มี **เวลาสูงสุด 30 นาที** หมดเวลาตัดสินด้วย HP ฐานแม่ที่เหลือ (เปอร์เซ็นต์)
- ชนะเมื่อ **ฐานแม่ฝ่ายตรงข้ามพัง** หรืออีกฝ่ายยอมแพ้/หลุดเกิน 60 วินาที

### 4.2 แผนที่
- สร้างจาก seed เหมือน Survival แต่ **สมมาตรแบบกระจก**: generate ครึ่งซ้ายแล้วสะท้อนข้ามแกน x (2v2 สะท้อน 2 แกน) ให้ทรัพยากรและภูมิประเทศเท่ากันทุกฝ่าย
- ฐานแม่อยู่ที่ x = ±38 กลางแผนที่ (x ≈ 0) เป็น **แหล่งแร่กลาง**: สายแร่เหล็กและเหมืองทองที่ไม่มีในฐานตัวเอง เพื่อบังคับให้ออกมาแย่ง
- แม่น้ำพาดกลางหรือขวางเส้นทาง มีจุดข้าม 2–3 จุดเป็นคอขวด ทั้งสองฝ่ายสร้างสะพานได้
- ขนาดเท่าเดิม (113×113) รัศมีก่อสร้างตามระดับฐานแม่เหมือน Survival แต่รัศมีสูงสุดไม่ทับกัน

### 4.3 เศรษฐกิจ (ตอบ [คำถาม] เรื่องกฎเต็มหรือกฎย่อ)
- **[เสนอ] กฎเต็ม แต่เร่งจังหวะ**: ทรัพยากร 5 ชนิด คนงาน ระดับฐานแม่ สิ่งปลูกสร้างชุดเดียวกับ Survival เพื่อไม่ต้องดูแลสองระบบ แต่
  - ไม่มี prep/battle: **1 วัน = 60 วินาที** เดินเอง (รายได้จ่ายทุก 60 วินาที) กลางวัน/กลางคืนวนอัตโนมัติ
  - ทรัพยากรเริ่มต้นสูงกว่า (ทอง 120 ไม้ 150 อาหาร 40) และราคาฐานแม่ L2 ลดลง ให้ 5 นาทีแรกมีอะไรทำ
  - เหมืองในฐาน **หมดหลัง 12 วัน** (ผลผลิตลดลงเรื่อยๆ) เหมืองกลางไม่หมด → กันการตั้งรับล้วน
- **[คำถาม]** ตัดไม้ด้วยตัวเองยังจำเป็นไหมใน PvP หรือให้โรงเลื่อยทำหมด (เสนอ: ยังตัดได้ แต่ให้ไม้เริ่มต้นพอสร้างโรงเลื่อยทันที)

### 4.4 การต่อสู้
- ศัตรูของหน่วยและป้อมคือ **ทุกอย่างของอีกทีม** (ยูนิต ฮีโร่ อาคาร) เป้าหมายลำดับ: หน่วยใกล้ > ฮีโร่ > อาคารป้องกัน > อาคารอื่น > ฐานแม่
- **คำสั่งใหม่ `attack`**: แตะบน minimap หรือกดค้างบนพื้น → หน่วยที่ตามฮีโร่และหน่วยว่างในรัศมี 9 เดินไปจุดนั้นแบบ attack-move (หยุดสู้เมื่อเจอศัตรู ไปต่อเมื่อเคลียร์) ปุ่ม "เรียกกลับ" ให้กลับมา hold ที่ฐาน
- ฮีโร่: 3 อาวุธเหมือนเดิม ตายแล้วฟื้นที่ฐาน 12 วินาที ฮีโร่ทำดาเมจอาคารได้ 50%
- **ตารางแพ้ทาง** (เพิ่มใน `UNITS`): ทหารราบ (หอก) ×1.5 ใส่อัศวิน, อัศวิน ×1.5 ใส่นักธนู, นักธนู ×1.3 ใส่ทหารราบ, บัลลิสตา ×2 ใส่อาคาร ทหาร ×0.5 ใส่กำแพงหิน
- ป้อมทำดาเมจยูนิตศัตรูตามปกติ ทหารต้องมี siege (บัลลิสตาเคลื่อนที่จากโรงหล่อ = สิ่งปลูกสร้างใหม่ระดับ 3) เพื่อทะลวงฐานที่ป้อมหนาแน่น
- stack ต่อคนใน PvP = **6** (ค่ากลาง) จำนวนหน่วยสูงสุดต่อฝ่าย 24

### 4.5 ข้อมูลที่มองเห็น (fog of war)
- **[เสนอ]** มี fog: มองเห็นในรัศมีของอาคาร (6) ยูนิต (7) ฮีโร่ (9) หอสังเกตการณ์ (14) ที่เหลือเป็นเทาและเห็นเฉพาะภูมิประเทศ
- server ส่งเฉพาะ entity ของศัตรูที่อยู่ในพื้นที่มองเห็นของทีมนั้น (ทำได้เพราะเป็น A)
- **[คำถาม]** เอา fog หรือไม่ ถ้าไม่มี PvP จะง่ายขึ้นมากทั้งเทคนิคและการเรียนรู้ของผู้เล่น แต่การซุ่มและสอดแนมจะหายไป

### 4.6 ความเท่าเทียม
- server สร้าง "โปรไฟล์กลาง" ให้ทุกคน (Power 0, Vitality 0, squad = 4 → stack 6, unlocks ครบ) ตามที่ระบุใน `02-meta-progression.md` ข้อ 7 engine ต้องรับโปรไฟล์เป็น input ไม่อ่านจาก D1 เอง
- ของตกแต่งเท่านั้นที่มาจากโปรไฟล์จริง
- ผล PvP **ไม่ให้ Ember** แต่บันทึกสถิติชนะ/แพ้ และ rating (ทีหลัง)

## 5. สถาปัตยกรรม (ทางเลือก A)

```
client (WebSocket)  ──input 10–20/s──▶  Durable Object "RoomSim"
                    ◀──snapshot 8/s──    ├─ world (engine.step ทุก 100ms)
                                         ├─ ตรวจ input/สิทธิ์ทีม
                                         ├─ ตัดข้อมูลตาม fog ต่อทีม
                                         └─ เขียนผลลง D1 เมื่อจบ
```

### 5.1 โปรโตคอล
- `join {code, token}` → server ตรวจ cookie/session ผ่าน Worker ก่อน upgrade WebSocket
- `input {x, z, commands[]}` เหมือนปัจจุบัน (seq/acks ใช้ต่อได้)
- `ready`, `surrender`, `ping`
- server → `snap {tick, world(ตัดแล้ว)}` ทุก 125ms และ `event {type, ...}` สำหรับสิ่งที่ต้องแสดงทันที (ฐานโดนตี, หน่วยตาย, ชนะ)
- ขนาด snapshot: World เต็มราว 40–60KB ที่ 8/s = 400KB/s **มากเกินไปสำหรับมือถือ** ต้องทำอย่างใดอย่างหนึ่ง
  - (1) ส่งเฉพาะ entity ที่เปลี่ยน (delta ต่อ tick) + snapshot เต็มทุก 5 วินาที
  - (2) บีบเป็น array ตัวเลขแทน object (ลดได้ราว 3 เท่า)
  - **[เสนอ]** ทำ (2) ก่อนใน sprint แรก แล้ว (1) เมื่อวัดแล้วยังหนัก

### 5.2 การจำลองบน server
- `engine.step` มีอยู่แล้วเป็น pure function ใช้ได้ทันที ต้องเพิ่ม `mode: 'pvp'` ให้ข้ามการสปอว์น wave และเปลี่ยนการเล็งเป้าเป็นตามทีม
- tick 10/s (dt 0.1 ซึ่งมากกว่า cap 0.05 ตอนนี้ → ต้องรัน step 2 ครั้งต่อ tick หรือปรับ cap)
- pathfinding flow field ต่อเป้าหมาย cache 40 รายการ ใน PvP เป้าหมายเยอะกว่า (หน่วยเล็งหน่วย) ต้องวัด CPU
- DO เก็บ world ใน memory และ checkpoint ลง storage ทุก 5 วินาที เพื่อกู้เมื่อ object ถูกย้าย

### 5.3 client
- แยก transport เป็น interface `RoomLink` (`send(input)`, `onSnapshot`) มี 2 implementation: `HttpLink` (co-op ปัจจุบัน) และ `SocketLink` (PvP) Game.tsx ไม่ต้องรู้ว่าใครจำลอง
- interpolation: เก็บ snapshot 2 อันล่าสุดแล้ว lerp ตำแหน่ง (scene ทำ lerp อยู่แล้วบางส่วน)
- ฮีโร่ของตัวเองใช้ client-side prediction เฉพาะการเดิน (แก้ตำแหน่งเมื่อ server ต่าง > 1.5)

### 5.4 ย้าย co-op มาใช้ด้วย (ทีหลัง)
เมื่อ A ทำงานแล้ว co-op ใช้ DO เดียวกันโดยเปิด wave NPC ปัญหา host หาย/host migration หายไปทั้งหมด และ late join ก็ง่ายขึ้น HTTP polling เก็บไว้เป็น fallback
